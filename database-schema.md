# Mithooos — Complete Database Schema Reference

**Database:** `mithooos` · PostgreSQL 14+ · schema: `public`
**Source files:** `backend/config/schema.sql` (primary — 18 tables + seed data), `backend/config/migration-phase5.sql` (supplementary notes, see bottom of this document)

This document consolidates the entire database structure into a single reference: every table, every column, every relationship, and the seed data that ships with the project.

## 1. Entity Relationship Overview

```
users ──┬──< orders ──< order_items >── products ──< product_images
        │        │                          │
        │        └──< payments              ├──< product_attributes
        │                                    ├──< product_reviews >── users
        ├──< wishlists >── products          └──< (category_id) categories (self-referencing parent)
        ├──< carts >── products
        ├──< addresses
        ├──< product_reviews
        ├──< blog_posts (as author)
        └──< audit_log (as admin)

coupons, newsletter_subscribers, settings, contact_messages  — standalone (no FKs)
```

**18 tables total**, grouped by purpose:

| Group | Tables |
|---|---|
| Identity | `users` |
| Catalog | `categories`, `products`, `product_images`, `product_attributes`, `product_reviews` |
| Shopping | `wishlists`, `carts` |
| Commerce | `orders`, `order_items`, `payments`, `addresses`, `coupons` |
| Marketing / Content | `newsletter_subscribers`, `blog_posts`, `contact_messages` |
| System | `audit_log`, `settings` |

## 5. Notes on `migration-phase5.sql`

This file is documented separately because it is **not a clean additive migration** — it partially overlaps and conflicts with the base schema:

- **Safe / additive:** adds `login_attempts`, `locked_until`, `reset_expires` to `users` (used by the brute-force lockout feature in `Auth.php`), and adds `is_primary`/`display_order` to `product_images` — both use `ADD COLUMN IF NOT EXISTS`, safe to run after `schema.sql`.
- **Conflicting:** its own `CREATE TABLE IF NOT EXISTS coupons` block uses **different column names** (`usage_limit`, `minimum_order`, `starts_at`, `expires_at`) than the coupons table actually defined in `schema.sql` and actually used by the application code (`max_usage`, `minimum_purchase`, `valid_from`, `valid_until`). Because `schema.sql` already creates `coupons` first, this second definition is a harmless no-op (`IF NOT EXISTS` skips it) — but it should not be treated as a second source of truth for the coupons table structure. **§2.13 above reflects the real, active column names.**
- **Duplicate seed data:** re-inserts categories and an admin user using PostgreSQL `ON CONFLICT DO NOTHING`, which is safe (no-op if already present) but redundant with `schema.sql`'s own seed section.

**Recommendation if maintaining this project going forward:** treat `schema.sql` as the single source of truth for table structure, and fold the two genuinely-new columns from `migration-phase5.sql` into it directly, then retire the migration file.
